# muphfasa-benchmarking

Scale benchmarks for [muphfasa](https://github.com/biboyd/muphfasa) on Aurora (Intel Data Center GPU Max, SYCL + MPI). This repo pulls `muphfasa` as a submodule (`external/muphfasa`) and adds large-scale benchmarks that don't belong in the core repo's regression tests.

## Benchmarks

| Case | Dim | Lattice | Sizes (weak) | Physics |
|------|-----|---------|--------------|---------|
| `tgv2d` | 2D | D2Q9 | 1024² → 8192² (1024²/GPU) | Taylor-Green vortex, periodic, analytical decay `exp(-2νk²t)` |
| `tgv3d` | 3D | D3Q19/27 | 128³ → 512³ (128³/GPU) | Taylor-Green vortex 3-D, periodic, `w=0` initial; NOT an exact N-S solution for t>0 (see `Tgv3dAnalytic.H`) |
| `lid2d` | 2D | D2Q9 | 1024² → 4096² (1024²/GPU) | Lid-driven cavity, closed square (NoSlip x-lo/x-hi/y-lo, `MovingWall` lid at y-hi), Re=100 (`inputs.bench`; override `units.Re`/`lbm.tau` for other Re) |
| `lid3d` | 3D | D3Q19/27 | 256³ → 1024³ (256³/GPU) | Lid-driven cavity, Re=100 (`inputs.bench`; override `units.Re`/`lbm.tau` for other Re), `MovingWall` |
| `beltrami3d` | 3D | D3Q19/27 | 128³ → 512³ (128³/GPU) | 3D Beltrami flow, fully periodic, exact N-S |

All share a single `bench.cpp` driver (thin clone of `external/muphfasa/tests/regression/couette/test_couette.cpp`) that times `advance()` without I/O and reports **MLUPS** (Million Lattice/cell Updates Per Second — the standard LBM community definition, `cells*steps/elapsed`, with no multiplication by the lattice's number of discrete velocities Q) alongside **MLUDPS** (the Q-scaled, roughly memory-bandwidth-proportional variant) for anyone who wants that figure instead.

## Quick Start (local, no Aurora)

```sh
git clone --recurse-submodules git@github.com:biboyd/muphfasa-benchmarking.git
cd muphfasa-benchmarking

# 2D TGV, 1024², 100 steps, no plotfiles
make -C benchmarks/tgv2d -j6 DIM=2
./benchmarks/tgv2d/bench2d.gnu.ex benchmarks/tgv2d/inputs.bench

# 2D Lid-driven cavity, 64², 100 steps, no plotfiles
make -C benchmarks/lid2d -j6 DIM=2
./benchmarks/lid2d/bench2d.gnu.ex benchmarks/lid2d/inputs.bench

# 3D Lid, 256³
make -C benchmarks/lid3d -j6 DIM=3
./benchmarks/lid3d/bench3d.gnu.ex benchmarks/lid3d/inputs.bench

# Weak scaling sweep (uses helper.py like couette). Each sweep point actually
# launches nprocs=nodes*ppn ranks via mpiexec; --max-grid-size is a fixed AMReX
# box tile size kept independent of --sizes so the domain is decomposed into
# enough boxes for those ranks to do real work (don't set it equal to the
# domain size, or every rank past the first sits idle on an empty box).
python3 run_scaling.py --case tgv2d --sizes 1024 2048 4096 --nodes 1 2 4 --ppn 1 --max-grid-size 64 --local
# Aurora: same sweep as PBS jobs (see Aurora section below)
# python3 run_scaling.py --case tgv2d --sizes 1024 2048 4096 --nodes 1 2 4 --dry-run
```

## Aurora

Builds on Aurora use SYCL + MPI + Intel. Batch scripts are generated by `batch/generate.py`, which bakes every parameter into a concrete PBS script so submission is just `qsub <script>` (no env vars on `qsub`).

```sh
# Build for Aurora (SYCL, MPI, Intel) — also done automatically by generated scripts
make -C benchmarks/tgv2d DIM=2 USE_MPI=TRUE USE_SYCL=TRUE COMP=intel
make -C benchmarks/lid2d DIM=2 USE_MPI=TRUE USE_SYCL=TRUE COMP=intel
make -C benchmarks/lid3d DIM=3 USE_MPI=TRUE USE_SYCL=TRUE COMP=intel

# Generate + submit (PBS, 12 ranks/node, 6 GPUs/node) — requires -l filesystems=flare
# Single job: 2 nodes, lid2d 2048², full pipeline (compile + validate + perf)
python3 batch/generate.py --case lid2d --nodes 2 --size 2048
qsub batch/generated/lid2d_2048_2nodes.sh

# Sweep: 2 and 4 nodes with 2048→4096, weak scaling (product of --nodes × --sizes)
python3 batch/generate.py --case lid2d --nodes 2 4 --sizes 2048 4096
# → batch/generated/lid2d_2048_2nodes.sh, lid2d_2048_4nodes.sh, lid2d_4096_2nodes.sh, ...

# 3D example with lattice override
python3 batch/generate.py --case lid3d --nodes 4 --size 256 --lattice D3Q19

# Validate-only or perf-only
python3 batch/generate.py --case lid3d --nodes 4 --stages validating
python3 batch/generate.py --case lid3d --nodes 4 --size 512 --stages performance

# Custom queue / allocation / walltime
python3 batch/generate.py --case tgv2d --nodes 8 --size 4096 --queue debug-scaling --project ABC123 --walltime 00:30:00

# Scaling wrapper (same sizes↔nodes pairing as run_scaling.py, but emits PBS scripts)
python3 run_scaling.py --case lid2d --sizes 1024 2048 4096 --nodes 1 2 4 --dry-run
```

Generated scripts live in `batch/generated/` (do not hand-edit — re-generate). Each stages compiles in the home checkout, then stages the exe + inputs to `/flare/<project>/$USER/muphfasa-benchmarking-runs/<case>_<size>_<nodes>nodes_<jobid>` and runs there (flare is required for `filesystems=flare`; the job `cd`s to `$PBS_O_WORKDIR` first). See `skills/aurora-overview.md` for queues (`debug` 1–2, `debug-scaling` 2–256, `prod` 256+), `qstat -u $USER` before submit, GPU binding (`gpu_tile_compact.sh` / `gpu_dev_compact.sh`), and proxy `proxy.alcf.anl.gov:3128`.

Local `run_scaling.py --local` still runs directly via `helper.run_bench` for quick dev — see Quick Start above and `benchmarks/README.md`. By default (no flag) it delegates to `batch/generate.py`.

## Layout

```
muphfasa-benchmarking/
  external/muphfasa/          # submodule, pinned SHA (update: git submodule update --remote)
  benchmarks/
    bench.cpp                 # generic timed driver (no analytic plotfiles)
    tgv2d/   GNUmakefile, inputs.bench, InitData.cpp (TGV, overrides src/Simulation/InitData.cpp)
    tgv3d/   GNUmakefile, inputs.bench, InitData.cpp, Tgv3dAnalytic.H (3-D TGV, borrows tgv2d+beltrami3d)
    lid2d/   GNUmakefile, inputs.bench (closed 2-D lid-driven cavity, walls on all four sides)
    lid3d/   GNUmakefile, inputs.bench (lid-driven, z-wall like couette)
             validate/ (closed cube, mass/KE/power-balance + Albensoeder Re=1000 extrema)
    beltrami3d/ GNUmakefile, inputs.bench, InitData.cpp, BeltramiAnalytic.H
  batch/
    generate.py               # PBS generator — bakes case/size/nodes/lattice/ppn/queue into a script
    generated/                # output of generate.py — qsub these (gitignored except examples)
  helper.py                   # shared build/run/parse helpers (from couette)
  run_scaling.py              # batch (default) → batch/generate.py, or --local → helper.run_bench
```

`Make.muphfasa` (`external/muphfasa/Make.muphfasa`) holds all solver sources and AMReX modules; each benchmark's `GNUmakefile` only sets `TOP`, `DIM`, `EBASE`, `CEXE_sources` and `include $(TOP)/Make.muphfasa`. Local `InitData.cpp` wins via `VPATH` precedence (`VPATH_LOCATIONS+=..` before include).

## Validate vs Perf

Plotfiles (`plt<step>`) are written in **physical (SI) units**, not lattice units —
`SimulationSetup::writeOutput` converts density/velocity via `UnitConverter::toPhysical`
before writing (upstream `muphfasa` commit `c736661`, "output in physical units"). The
solver's internal state stays in lattice units; only I/O is converted. Any `InitData.cpp`
override (`tgv2d`, `beltrami3d`) takes `const UnitConverter&` and must convert its IC
amplitude from the physical `units.ref_velocity` via `units.toLatticeVelocity()` — see
either file for the pattern. A correctness-check driver that writes its own analytic
plotfile (like `beltrami3d/validate/test_beltrami3d.cpp`) must likewise convert its
analytic solution to physical units before `fcompare`, or the comparison will be
comparing physical sim output against a lattice-unit analytic field and report bogus
errors.

- **Validate** (small, correctness): `inputs` with `amr.plot_int=200`, fcompare vs analytic – same as regression.
  - `tgv2d`: validated upstream, `external/muphfasa/tests/regression/tgv2d` (exact 2D TGV decay).
  - `beltrami3d`: validated in this repo, `benchmarks/beltrami3d/validate/` (exact 3D Beltrami decay,
    mirrors the tgv2d test — see its README for build/run/fcompare steps).
  - `tgv3d`: `benchmarks/tgv3d/validate/` is not an `fcompare`-vs-analytic test like the other
    two — the classic 3-D TGV IC has no closed-form solution for t>0 (vortex stretching moves
    energy into other modes, unlike the 2-D TGV or the Beltrami flow, see `Tgv3dAnalytic.H`), so
    there's no analytic field to diff against. Instead `test_tgv3d.cpp` checks the **global
    kinetic-energy balance** `KE(0)-KE(T) = nu*integral(|curl(u)|^2)dt`, which is exact for
    incompressible Navier-Stokes at any Re/amplitude/duration regardless of vortex stretching —
    a genuine correctness check on the solver, not just a sanity check on the IC wiring.
  - `lid2d`: no closed-form solution either. `benchmarks/lid2d/validate/` runs the cavity to steady
    state and checks mass conservation, KE spin-up/plateau, the lid-power vs viscous-dissipation
    balance, and the Re=100 centerline extrema of Ghia, Ghia & Shin, J. Comput. Phys. 48(3), 387-411
    (1982), doi:10.1016/0021-9991(82)90058-4 (see its README for the values and tolerances).
    Exits nonzero on failure. **It currently fails on the pinned `external/muphfasa`** because of a
    bounce-back bug on diagonal links (`muphfasa_issues.md` item 8); it passes with the one-line
    fix described there.
  - `lid3d`: like `lid2d`, no closed-form solution. `benchmarks/lid3d/validate/` runs the closed cube (NoSlip on all faces except the `MovingWall` lid at z-hi) to steady state and checks mass, KE spin-up/plateau, power balance, and — at Re=1000 (`inputs.re1000`) — the cubical-cavity extrema of Albensoeder & Kuhlmann, J. Comput. Phys. 206(2), 536-558 (2005), doi:10.1016/j.jcp.2004.12.024 (Table 10; see `benchmarks/lid3d/validate/README.md` for the paper→code coordinate mapping). Exits nonzero on failure; also fails on the pinned `muphfasa` until `muphfasa_issues.md` item 8 is fixed.
- **Perf** (large, no I/O): `inputs.bench` with `amr.plot_int=-1`, `sim.max_step`/`bench.warmup` = 2100/100 (2D: 2000 timed) or 550/50 (3D: 500 timed), `lbm.tau=0.8`, measure `MLUPS`.

## Performance History (`results/history.jsonl`)

`perf.py log` (and `run_scaling.py`, which calls it) appends a row to the git-tracked
`results/history.jsonl` + `.cache/perf.db` whenever it runs on the `main` branch — there is
**no CI gate yet**. In practice this means `results/history.jsonl` today is "whatever anyone
happened to run locally on `main`," not a curated/vetted performance record: a noisy laptop run
or a one-off wrong build flag becomes part of the permanent history just like a clean Aurora
run. Each row's `ci` field (0 for all current rows) and `hostname` (part of the dedup key, so
different machines don't collide) let you filter by provenance when reading the history. Wiring
up CI-only ingestion so `main` pushes are the only trusted source is tracked as future work in
`/home/biboyd/.opencode/plan/benchmark-perf-db.md` (§6) — until then, treat `history.jsonl`
rows as indicative, not authoritative, unless you know who ran them and on what.

See `benchmarks/README.md` for problem sizes, Re/tau, and expected MLUPS on Aurora.
